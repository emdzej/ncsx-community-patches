# ncsx community patches

Community-contributed coding patches for **[ncsx](https://github.com/emdzej/ncsx)** —
small YAML files (`.ncsxpatch.yaml`) that describe FSW/PSW changes one
or more BMW ECU modules need for a specific feature retrofit, codename
swap, or behaviour tweak.

The browser app at <https://ncsx.bimmerz.app> reads these files
directly via **Apply patch…**.

## Layout

```
patches/
├── E46/
│   ├── README.md                           # ← auto-generated
│   ├── drl-via-parking-lights.ncsxpatch.yaml
│   ├── ezs-disable-seatbelt-gong.ncsxpatch.yaml
│   ├── pre-facelift-drl.ncsxpatch.yaml
│   ├── pre-facelift-drl/                   # ← supporting files (same basename)
│   │   ├── LCM_E46_modified.C06.dat
│   │   └── notes.md
│   └── …
├── E60/
│   ├── README.md                           # ← auto-generated
│   ├── comfort-access.ncsxpatch.yaml
│   └── …
└── README.md                               # ← auto-generated (chassis index)
```

- One folder per chassis (`E46`, `E60`, `E89`, `F30`, …).
- One file per feature. Filename = kebab-cased feature name + the
  full `.ncsxpatch.yaml` suffix.
- A patch can touch multiple modules in one file (e.g. Comfort Access
  needs CAS + LCM + KOMBI) — keep the whole feature together, don't
  split it across files.
- **Supporting files** (modified DATEN files, traces, screenshots,
  extended notes) go in a folder **alongside** the patch with the
  same basename — strip the `.ncsxpatch.yaml` suffix and use the
  remaining stem as the folder name. Example:
  `pre-facelift-drl.ncsxpatch.yaml` → folder `pre-facelift-drl/`.
  Keeps a feature's artefacts together without cluttering the
  chassis directory, and the contributing PR adds both the YAML
  and its companion folder in a single review.

The `README.md` files under `patches/` are **regenerated by CI** on
every push to `main` that touches a patch — don't hand-edit them.

## Contributing

1. **Author the patch** in the ncsx web app: stage edits in the
   FunctionTree, click **Save as patch…**, fill in title /
   description / author / keywords. Optionally tick **Pin coding
   index** and **Capture require_current**.
2. **Confirm it works** on a real chassis. Read the ECU back after
   `SG_CODIEREN` and verify the change took effect. Patches that
   haven't been tested in-car aren't ready to share.
3. **File it** under `patches/<CHASSIS>/<kebab-title>.ncsxpatch.yaml`.
   Use the canonical chassis code (`E46`, `E60`, `E89`, `F10`, …).
4. **Open a PR.** The validate workflow checks schema + naming. Once
   merged, the index workflow regenerates the chassis READMEs.

### What makes a good patch

- **Descriptive title.** "DRL via parking lights (E46 LCM)" beats
  "DRL patch".
- **Description that explains the feature**, prerequisites
  (hardware retrofit? FA codes? other modules?), and the source
  if known (Bentley §, BMW TIS bulletin, forum thread).
- **Use `require_current`** for changes where applying on top of an
  already-modified ECU would be dangerous or misleading. The web app
  refuses the apply on mismatch unless the user explicitly overrides.
- **Pin `coding_indexes`** when the patch was verified against
  specific CABD variants. CABDs are versioned; FSWs occasionally
  move between revisions. Pinning narrows the "applies cleanly"
  window for users.
- **One feature per file.** "Enable DRL + change welcome sound +
  disable seatbelt gong" should be three patches, not one — users
  pick which to apply.

### Schema reference

The `.ncsxpatch.yaml` v1 schema is fully documented in the ncsx repo:
**[docs/patches.md](https://github.com/emdzej/ncsx/blob/main/docs/patches.md)**.

Quick example:

```yaml
schema: ncsx-patch/v1
title: DRL via parking lights (E46 LCM)
description: |
  Activates running lights through the front parking lamps when
  ignition is on. Standard Euro feature; missing on US-spec cars.
author: emdzej
keywords: [DRL, lights, retrofit, us-spec]
chassis: E46

modules:
  - module: LCM
    coding_indexes: [C06, C07]
    require_current:
      TFL_LICHTHUPE: nicht_aktiv
    edits:
      TFL_FUNKTION: aktiv
      TFL_LICHTHUPE: aktiv
      STANDLICHT_TFL: aktiv
```

## How the auto-generated indexes work

Two GitHub workflows under `.github/workflows/`:

- **`validate.yml`** — runs on every PR. Schema-checks every
  `.ncsxpatch.yaml`, warns on dir-vs-chassis mismatches, fails on
  parse/schema errors.
- **`build-indexes.yml`** — runs on push to `main` when a patch file
  changes. Regenerates `patches/README.md` (chassis list) and
  `patches/<chassis>/README.md` (patches grouped by module), commits
  back. The commit only touches `README.md` files, which are
  outside the workflow's path filter, so the auto-commit doesn't
  re-trigger the workflow.

Run them locally before opening a PR:

```bash
npm install
npm run validate         # schema-checks every patch
npm run build-indexes    # regenerates README.md files (also handy for previews)
```

## Browsing patches

- **By chassis** → [`patches/`](patches/) (auto-generated index).
- **All patches in one chassis** → `patches/<CHASSIS>/README.md`,
  grouped by module.
- **In the app** → load the chassis + module, click **Apply patch…**,
  pick a `.ncsxpatch.yaml`. The app filters to entries matching the
  current module + flags chassis / coding-index mismatches before
  staging anything.

## Disclaimer

Patches here are contributed by users, not vetted by the ncsx
maintainers or by BMW. Coding mistakes can brick modules. Applying a
patch is your responsibility:

- Read what it changes — patches are plain text.
- Confirm the patch's `chassis` matches yours.
- Have your current coding exported (`FSW_PSW.TRC`) before writing,
  so you can roll back.
- Don't apply patches from sources you don't trust.
